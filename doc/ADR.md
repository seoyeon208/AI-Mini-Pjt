# 아키텍처 결정 기록

2026-10-21 현재 구현을 기준으로 정리한 사후 기록이다. 제안만 된 기능을 구현한 것으로 기록하지 않는다.

## 1. 수업의 LangGraph 흐름 유지

- 결정: route → plan → gate → research → replan_check → analysis → write → validate → finalize를 유지한다. 일반 대화와 단순 조회에는 필요한 노드만 실행한다.
- 이유: 수업의 계획·실행·검증 책임을 코드에서 확인할 수 있고, 단순 질문에 복합 진단 비용을 쓰지 않는다.
- 대안과 한계: 하나의 프롬프트로 합치면 짧아지지만 계획과 검증을 독립적으로 제어하기 어렵다. 현재는 역할별 노드 구조이며 독립적인 에이전트 프로세스나 에이전트 간 협상 구조는 아니다.
- 근거: `agent/graph.py`, `agent/deps.py`, `tests/test_routing.py`, `tests/test_gate.py`.

## 2. 소규모 매뉴얼에 BM25 검색 적용

- 결정: 매뉴얼 6개를 문서 단위로 검색하고, MCP Resource에서 원문을 읽는다.
- 이유: 현재 자료량에서 별도 임베딩 모델·벡터 DB 없이 검색 결과와 원문 출처를 설명할 수 있다.
- 대안과 한계: 의미 검색은 표현 변화에 유리하지만 구성과 평가 범위가 늘어난다. 현재 BM25는 동의어·간접 표현을 놓칠 수 있다. 문서·질문이 늘어나면 검색 누락 사례를 근거로 재검토한다.
- 근거: `runbook_search.py`, `mcp_server.py`, `evaluation/INCIDENT-QUALITY.md`.

## 3. 조회는 원문 구성, 진단은 모델 작성 후 검증

- 결정: 단순 조회는 원문을 정형화한다. 복합 진단의 관측값·조치는 코드가 원문에서 구성하고, 모델은 가설·근거 번호·확인할 자료를 작성한다. 코드 검사와 문장별 LLM 검수 후 공개한다.
- 이유: 측정값과 조치 조건을 모델이 재생성하면서 바꾸는 오류를 줄인다. 추가 조사와 재작성은 각각 최대 1회로 제한한다.
- 대안과 한계: 모든 내용을 자유 생성하면 표현은 유연하지만 근거 대조가 어려워진다. 현재도 가설의 인과관계와 검수 모델 판단까지 보장하지는 않는다. 진단 답변은 검증 이후 한 번에 공개하므로 토큰별 진단 스트리밍은 제공하지 않는다.
- 근거: `agent/reporting.py`, `agent/graph.py`, `evaluation/REVIEW-QUALITY.md`.

## 4. 모델 호출과 서버 응답 처리 분리

- 결정: 동기 모델 호출을 `asyncio.to_thread`로 실행해 이벤트 루프를 막지 않는다. 모델 연결 실패·시간 초과는 HTTP 오류 또는 SSE `RequestFailed`로 안내하고 자동 재전송하지 않는다.
- 이유: 실제 복합 진단 중 `/health` 요청이 2초 제한에 연속 3회 실패했다. 기존 모델 인터페이스를 유지하는 작은 수정으로 상태 확인과 스트리밍 처리를 계속할 수 있게 한다.
- 대안과 한계: 전 모델 인터페이스를 비동기로 바꾸는 작업은 범위가 더 크다. 스레드로 넘긴 HTTP 호출은 브라우저 연결이 끊겨도 즉시 종료되지 않을 수 있으며 기존 호출 제한 시간까지 남을 수 있다. 모델 추론 자체가 빨라지는 변경은 아니다.
- 근거: `tests/test_service_failures.py`, `evaluation/INTEGRATION-CHECK.md`.

## 5. 세션 기록은 SQLite에 보관

- 결정: 요청마다 thread_id로 대화 이력을 읽고, 성공한 응답을 파일 기반 SQLite에 저장한다.
- 이유: 서버 메모리에 세션을 고정하지 않고 동일한 DB 파일을 재사용할 수 있다.
- 대안과 한계: 로컬 단일 서버용 구성이다. 여러 머신에서 DB를 공유하는 분산 무상태 배포를 검증한 것은 아니다. 일반 대화는 이력을 사용하지만 진단의 이전 대상·시점 비교는 자동 복원하지 않는다. UI에서 선택한 서비스는 다음 요청에 다시 명시된다.
- 근거: `agent/session_store.py`, `server.py`, `web_chat.html`.

## 6. 독립적인 MCP 요청은 같은 세션에서 동시 실행

- 결정: MCPClient의 응답 대기 전체를 감싸던 공통 잠금을 제거한다. 기존 research의 gather를 그대로 사용한다.
- 이유: 설치된 SDK는 요청 ID별로 대기 응답을 관리한다. 클라이언트의 추가 잠금 때문에 gather로 시작한 조회도 서버에서는 순차 실행되고 있었다.
- 대안과 한계: 요청마다 새 연결을 만들거나 서버별 잠금으로 바꾸면 연결 비용이 늘거나 같은 서버 안의 직렬화가 남는다. 자료 의존성이 있는 단계는 유지하고 원문 조회는 순차 처리한다. 대규모 동시 사용자 부하나 외부 서버의 요청 제한까지 검증한 것은 아니다.
- 근거: 실제 stdio 서버에서 실행 구간 겹침, 역순 완료 시 응답 대응, 도구 일부 실패, 요청 취소 이후 세션 재사용을 검사했다. `tests/test_mcp_concurrency.py`, `evaluation/MCP-CONCURRENCY.md`.
