# MCP 동시 실행 검증

2026-10-21. 변경 범위는 `agent/mcp_client.py`의 공통 잠금 제거다. LLM·검색·검증 정책과 화면은 변경하지 않았다.

## 문제와 수정

Research는 모니터링 작업과 검색 작업에 각각 `asyncio.gather`를 사용했지만,
MCPClient가 응답을 기다리는 전체 구간을 하나의 `asyncio.Lock`으로 감쌌다.
따라서 같은 서버뿐 아니라 다른 서버 요청까지 서로 기다렸다.

설치된 MCP SDK의 `ClientSession.send_request`와 JSON-RPC dispatcher를 확인했다.
SDK는 요청마다 ID를 발급하고 해당 ID의 대기자에게 응답을 전달한다.
클라이언트의 추가 잠금을 제거하고 이 처리를 그대로 사용한다.
SDK 자체의 통신 제어를 수정하거나 요청마다 새 세션을 만들지 않았다.

자료 의존성은 유지한다. 모니터링 결과를 받은 뒤 알림으로 검색하고, 검색된 문서의 원문을 읽는다.
각 단계의 독립적인 모니터링·검색 요청은 동시 실행하며 원문 조회는 기존처럼 중복 제거 후 순차 실행한다.
`parallel_elapsed`는 Research 전체 경과 시간이므로 순수 병렬 구간의 시간으로 해석하지 않는다.

## 실제 프로토콜 검증

`tests/fixtures/concurrent_mcp.py`는 별도 프로세스에서 실행되는 FastMCP 서버다.
생산 MCPClient가 실제 stdio로 호출하며 세 요청에 0.20 / 0.06 / 0.12초의 비동기 지연을 넣었다.
서버가 각 호출의 시작·종료 시각을 기록하므로 클라이언트의 작업 시작 시각만으로 병렬 실행을 추정하지 않는다.

- 변경 전: 새 테스트 3개 중 실행 겹침을 검사하는 2개가 실패했다.
- 변경 후: 세 호출 모두 `가장 늦은 시작 < 가장 빠른 종료`를 만족했다.
- 늦게 요청한 짧은 조회가 먼저 끝나도 서비스명과 CPU 값이 원래 요청에 정확히 연결됐다.
- Research에서 한 도구가 실패해도 나머지 두 결과와 완료 상태를 유지하고, 실패 대상만 `tool_error`로 남겼다.
- 한 호출을 취소해도 다른 호출이 성공했고 같은 세션에서 다음 요청도 성공했다.
- 전체 회귀 테스트: **90개 통과**, 7.159초. 기존 실제 MCP·HTTP/SSE 테스트도 포함한다.

실패 테스트는 의도적으로 도구 오류를 발생시키므로 서버 오류 로그가 출력된다. 기존 SDK 구 필드명 접근 경고는 남아 있다.

## 동일 조건 시간 비교

각 방식 3회, 서버 시작 시간 제외, 첫 호출 사전 준비 없음. 표는 중앙값이다.
변경 후 측정은 자동 테스트와 함께 실행했으며, 성능 보장용 부하 시험은 아니다.

| 상태 | 호출 방식 | 중앙값 | 세 호출 동시 실행 |
|---|---|---:|---:|
| 변경 전 | 순차 await | 0.396845초 | 0/3회 |
| 변경 전 | gather + 공통 잠금 | 0.396600초 | 0/3회 |
| 변경 후 | 순차 await | 0.387766초 | 0/3회 |
| 변경 후 | gather | 0.202936초 | 3/3회 |

변경 전후 gather 시간은 이 조건에서 약 **48.8% 감소**했다. 모든 측정의 서비스명·CPU 결과는 동일했다.
이는 지연을 넣은 세 도구 호출의 결과이며 실제 모니터링 처리량이나 AI 답변 전체의 속도 개선률이 아니다.
기본 예시 모니터링은 짧은 파일 조회이므로 실제 체감 차이는 작을 수 있다.

원시 시간·서버 실행 구간·소스 해시는 [mcp-concurrency.json](mcp-concurrency.json)에 보관한다.
확인한 환경은 Python 3.11, MCP 2.3.0, FastMCP 4.1.1이다. 다른 SDK 버전의 병렬 동작까지 검증한 것은 아니다.

## 재현

프로젝트 루트에서 실행한다. 외부 모델·API 키·사용자 DB는 필요하지 않다.

```bash
LANGCHAIN_TRACING_V2=false LANGSMITH_TRACING=false .venv/bin/python3 -m unittest discover -s tests -p test_mcp_concurrency.py -v
LANGCHAIN_TRACING_V2=false LANGSMITH_TRACING=false .venv/bin/python3 -m unittest discover -s tests -q
```

위 테스트는 실제 실행 겹침·응답 대응·부분 실패·취소 격리를 재현한다. 시간 비교를 재현하려면 같은 fixture 서버에서
`auth-service`, `payments-service`, `gateway-service`를 순차 await와 gather로 각각 3회 호출하고
`time.perf_counter()`로 전체 호출 시간을 잰다. 현재 코드로는 잠금 제거 이전 결과가 재현되지 않으며,
변경 전 수치는 JSON에 기록한 이전 소스 해시에 해당한다.

대규모 사용자 부하·외부 MCP 서버의 호출 제한·서버 재연결은 이번 범위에 포함하지 않았다.
다음 제출 요건은 LangSmith 추적 수신과 고정 질문 비교 평가의 증거 확인이다.
