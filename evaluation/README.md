# 실제 모델 평가

일반 대화·상태 조회·매뉴얼 검색·복합 분석·잘못된 요청을 각각 3개씩 평가한다.
`cases.json`의 질문, 허용 경로, 조사 대상, 관련 문서, 차단 여부는 개선 전에 정했다.
이는 이 프로젝트를 위한 소규모 개발 평가이며, 일반적인 모델 정확도를 뜻하지 않는다.

모델 변경 결과는 [1차 평가](RESULTS.md), 조회 답변 개선과 남은 실패 사례는 [2차 평가](ANSWER-QUALITY.md)에 정리했다.
검색·근거 검사 및 복합 답변 검수 변경은 [복합 진단 개선 기록](INCIDENT-QUALITY.md)에 정리했다.
이후 문장 번호 검수와 관측·가설 분리 결과는 [검수 보완 기록](REVIEW-QUALITY.md)에 정리했다.

## 실행

프로젝트 루트에서 가상환경을 활성화하고 Ollama가 실행된 상태로 진행한다.

```bash
mkdir -p evaluation/runs
python evaluation/run.py evaluation/runs/new-run.json
# 고정 질문 중 복합 진단 3개만 재평가
python evaluation/run.py evaluation/runs/new-incidents.json --group incident
# 기존 복합 질문과 표현을 바꾼 질문 각 3개
python evaluation/run.py evaluation/runs/new-review.json --cases evaluation/review-cases.json
# 정상·의도적 오류 대조 (기본 2B, --model로 설치된 다른 모델과 비교 가능)
python evaluation/check_semantics.py evaluation/runs/new-run.json evaluation/runs/new-semantics.json
```

`evaluation/runs/`는 Git에서 제외된다. 기존 결과 파일은 덮어쓰지 않는다. 새 실행에는 다른 파일명을 지정한다.
질문별 결과가 끝날 때마다 저장되므로 중단된 평가도 완료된 질문까지 확인할 수 있다.
`--baseline`은 분류 모델을 이전 0.6B 설정으로 바꾸는 옵션이다. 과거 소스까지 복원하지 않으므로,
현재 코드에 이 옵션만 붙여 실행한 결과를 과거 구현의 재현 결과로 해석하면 안 된다.

## 비교 조건

- 1차 비교(`before.json` → `after.json`)는 fast=`qwen3:0.6b`에서 `qwen3.5:2b`(`think=false`)로 변경했다.
- 2차 비교(`after.json` → `answer-quality.json`)는 모델을 유지하고 조회 답변을 원문 구성·대조로 바꿨다. 복합 진단은 quality=`qwen3:8b`의 작성·검수를 유지하되 프롬프트와 수치 검사도 개선했다. 검증 방식이 달라졌으므로 전체 통과율을 모델 정확도 향상으로 해석하지 않는다.
- 현재 복합 진단 평가는 분석·작성에 8B, 사실 검수에 2B를 사용한다. 임의의 품질 점수 대신 모든 문장의 판정과 근거 번호를 받는다. 이전 검수 통과율과는 판정 방법이 다르며, 답변 내용과 정상·오류 대조 사례를 함께 확인해야 한다.
- 실제 로컬 모델, LangGraph와 MCP를 사용한다.
- 모델을 사전 로드한 뒤 질문별 총 소요 시간과 노드별 시간을 측정한다. 토큰 생성까지 포함하며 서버 시작 시간은 제외한다.
- 실제 모니터링 MCP 호출 뒤, 반환값을 `data/monitoring.json`의 고정값으로 바꾼다. 원래 도구의 무작위 수치 변화가 비교에 영향을 주지 않게 하기 위함이다.
- 첫 호출의 테스트용 시간 초과는 비활성화한다. 검색·원문·표준 절차는 실제 MCP 응답을 사용한다.
- 각 질문은 빈 대화 이력으로 시작한다. 사용자 세션 DB를 사용하지 않으며 LangSmith 외부 전송도 끈다.
- 모델 정보, 질문 파일 해시, 주요 코드 해시와 원본 결과를 JSON에 기록한다.
- 같은 기기여도 캐시, 메모리 상태, 발열, 생성 결과에 따라 시간이 변한다. 각 1회 측정값은 반복 측정에 따른 성능 보장 수치가 아니다.

## 판정 기준

- 경로 일치: 정해 둔 허용 경로에 들어갔는지 확인한다.
- 조사 범위: 최종 관측 시스템이 기대 시스템과 정확히 일치하는지 확인한다.
- 대상 확인 요청: 미등록·미지정 대상은 조회를 진행하지 않고 사용자에게 확인을 요청해야 한다.
- 검색 정밀도: 관련 문서 수 / 전체 반환 문서 수. 재현율: 반환한 관련 문서 수 / 기대 문서 수. 질문별 중복 문서는 한 번만 센다.
- 사실 대조: 코드의 관측값·수치 비교·문서 출처·조치 원문 검사를 기록한다.
- 정상·오류 대조: `check_semantics.py`는 코드 검사 후 통과한 사례만 모델로 검수한다. 차단 단계와 문장 참조 유효성을 구분해 기록한다. 전체 판정 일치를 모델 단독 정확도로 해석하지 않는다.
- 답변 내용: 저장된 답변을 별도로 읽어 요청 충족과 근거 없는 단정을 확인한다. LLM 자체 검증 통과율과 구분한다.

복합 분석의 관련 문서는 질문과 고정된 알림을 함께 보고 지정했다. 예를 들어
`payments-service`에는 CPU 경고 외에 응답 지연 알림도 있어 `high-latency`를 관련 문서로 포함한다.
